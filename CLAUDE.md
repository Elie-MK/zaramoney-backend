# CLAUDE.md — ZaraMoney Backend

Fintech wallet backend (P2P transfers, agent withdrawals, admin deposits) for a mobile app (Expo / React Native client, not in this repo).

## Stack
- JHipster 8.11.0 monolith, **no client** (`skipClient: true`); Spring Boot 3.4.5, Java 17, Maven (`./mvnw`)
- PostgreSQL + Liquibase, Hibernate L2 cache (Ehcache)
- JWT auth (HS512, JHipster `SecurityJwtConfiguration`), stateless
- Cloudinary for KYC images (`CloudinaryConfig`, `UploadFileService`)
- Expo push notifications (`ExpoPushService`, WebClient → `https://exp.host/--/api/v2`)
- Package root: `com.zekodnix.zaramoney`

## Commands
- Run dev: `./mvnw` (profile `dev`); DB: `npm run docker:db:up`
- Tests: `./mvnw verify` (or `npm run backend:unit:test`). Integration tests (`*IT`) use Testcontainers Postgres (version pinned to 1.21.4 in the pom for Docker 29). Single IT: `-Dtest=NoSuchTest -Dsurefire.failIfNoSpecifiedTests=false -Dit.test=SomeIT -Dfailsafe.failIfNoSpecifiedTests=false`
- Local secrets: copy `.env.example` → `.env` (git-ignored, loaded by the dev profile). Prod reads them from environment variables (no defaults)
- Prod jar: `./mvnw clean package -Pprod -DskipTests`
- Format: `npm run prettier:format` (Prettier + prettier-plugin-java; husky pre-commit runs lint-staged)

## Code conventions — the "Plus" pattern
JHipster-generated files (`*Service`, `*Resource`, `*QueryService`, `*Mapper`, `*Criteria`, domain, DTOs, Liquibase changelogs from `.jhipster/*.json` / `app.jdl`) are kept close to generated output.
**Custom business logic lives in `*Plus` classes**, which wrap the generated services:
- `service/*ServicePlus.java`, `web/rest/*ResourcePlus.java`
- Other custom code: `BackOfficeService`/`BackOfficeResource` (`/api/admin/backoffice`), `UserAccountService`/`UserAccountController` (`/api/user-account`), `TransactionValidatorService`, `UploadFileService`, `CloudinaryService`, `ExpoPushService`, `service/utils/MaskingUtils`
- Custom request bodies are in `web/rest/vm/` (`TransactionRecordVM`, `WithdrawalTransactionRecordVM`, `UserAccountVM`)

Prefer putting new logic in `*Plus` classes rather than editing generated files, unless the generated file itself is the problem (e.g. security on generated CRUD resources).

## Domain
Entities: `User` (login = email), `UserDetailsAccount` (KYC, phone, isAgent, expoPushToken), `BankAccount` (accountNumber unique, balance decimal(21,2), currency, status), `TransactionRecord`, `LedgerEntry` (DEBIT/CREDIT), `TransactionFee`, `TransactionLimit`, `IdempotencyRecord` (key_hash unique), `Notification`. Hand-written (not JHipster): `TransactionPin` (table `transaction_pin`; never expose it via DTO/CRUD), `UserSession`, `RefreshToken`, `AccessBlock`, `AuditEvent` (append-only). They are still declared in `app.jdl` (with `skipServer`, excluded from dto/service/paginate/filter) so the JDL documents the whole model; keep `.jhipster/*.json` in sync (validate with `npx generator-jhipster@8.11.0 jdl app.jdl --json-only` in a scratch copy). Regenerating an existing entity must not rewrite its applied changelog (`--skip-db-changelog`). Schema changes not generated by JHipster go in `liquibase/changelog/2026111200000*_*.xml`-style hand-written changesets.

## Money flows (key files)
- **P2P send** — `POST /api/plus/transaction-records/send` → `TransactionRecordServicePlus.createTransactionRecord` (deliberately NOT `@Transactional`):
  1. idempotent replay (read-only tx; key scoped per user + request hash) → 2. KYC must be `VERIFIED` → 3. `TransactionPinService.verifyPin` (own REQUIRES_NEW tx, **before** the main tx — never nest it, the test pool has 1 connection and prod would starve) → 4. one `TransactionTemplate` tx: reserve idempotency (`saveAndFlush`) → counterparty (`findCustomerAccount`) → sender (`resolveSenderAccountNumber`) → `lockAccounts` (PESSIMISTIC_WRITE, ordered by account number) → `requireOwnedBy` → `checkAccounts` (both ACTIVE, same currency, no FX) → fee (`FeeSchedule`) → `checkAmountValidation(amount, fee, …)` → `checkLimits` → `move()` (on the locked managed entities; never `save(dto)` a locked account) → fee record + ledger → complete idempotency → notifications
  - Both endpoints go through ONE private `execute(MoneyRequest)`; a new customer money flow should be a new `MoneyRequest`, not a copy. `transactionType` is set by the server
- **Withdrawal to agent** — `POST /api/plus/transaction-records/withdrawal` → `withdrawalTransaction`, same structure (receiver must have `isAgent`)
- **Sender account**: optional `senderAccountNumber` on both (`resolveSenderAccountNumber`; required if the user has several accounts); ownership re-checked on the locked row
- **Fees / revenue**: ledger per transfer = DEBIT sender `amount + fee`, CREDIT receiver `amount`, CREDIT SYSTEM fee revenue `999900000003` `fee` (`recordFeeAndLedger`; lock the fee account last). `validateDoubleEntry(List)` checks Σdebits == Σcredits. Income report: `RevenueReportService` → `GET /api/admin/backoffice/reports/revenue?from&to&groupBy=day|month|year`. System accounts (`SystemAccountService`): promo `…0001`, settlement `…0002`, fee revenue `…0003`; always locked after customer rows
- **Ledger** (`LedgerEntryServicePlus.buildEntry`): pass the DTO of the LOCKED account taken AFTER its balance changed (stored as `balance_after`; currency = account currency). `ledger_entry` is append-only (DB trigger; admin CRUD read-only): never update/delete entries, post a correcting transaction. Test clean-up must run `MoneyTestData.LEDGER_MAINTENANCE` first in the same transaction. Daily check: `LedgerReconciliationService` (`GET /api/admin/backoffice/reports/reconciliation`)
- **Responses to customers** are `TransactionReceiptDTO` (`TransactionReceiptService`): never another user's balance/email/ids. Lists/details are scoped to the current user (404 otherwise)
- **Admin deposit** — `POST /api/admin/backoffice/user/deposit` → `BackOfficeService.addMoneyToUserAccount` (one `@Transactional`: idempotency per admin, lock customer row then the SYSTEM settlement account `999900000002`, DEBIT settlement / CREDIT customer). `idempotencyKey` required
- **Onboarding/KYC** — `POST /api/user-account/create` (multipart, both pictures required) → one account per user (409 otherwise), private Cloudinary uploads (`UploadFileService`, refs `"<publicId>.<format>"`), USD `BankAccount` at 0 + default `TransactionLimit` + $5 bonus (`SignupBonusService`, from the SYSTEM promo account `999900000001` through the ledger), KYC `PENDING`. Admin review: `/api/admin/backoffice/kyc…` (`KycReviewService`)
- **Fraud**: `FraudScoringService.assess` runs in `execute()` after the limits, under the locks (rules + weights in `application.fraud`; `mode` monitor|enforce). Result stored on the transaction (`riskScore`, `fraudStatus`, `fraudReasons`); in enforce mode a BLOCKED payment throws `FraudBlockedException` → rollback, attempt saved FAILED in a new (not nested) tx, 403 `transactionblocked`. Customers only ever see COMPLETED transactions. Review queue: `FraudReviewService`
- **Audit**: every admin action and sensitive customer change calls `AuditService.record(AuditAction, targetType, targetId, details)` inside its own transaction (rolls back with it). `audit_event` is append-only (trigger). Add an `AuditAction` value (text; never rename one) for any new admin endpoint. Query: `GET /api/admin/backoffice/audit`
- **Row locks**: lock accounts only with `BankAccountRepository.findByAccountNumberForUpdate` / `findByIdForUpdate` (`BankAccountLocking`: lock, then refresh). Never add a plain `@Lock` query for an entity that may already be loaded in the transaction: Hibernate keeps the stale state (lost updates)
- **Account types**: `BankAccountType.CUSTOMER` (balance ≥ 0, DB check constraint) vs `SYSTEM` (no user, may go negative, never a customer counterparty). Use `BankAccountServicePlus.findCustomerAccount` for any user-supplied account number
- **PIN**: `TransactionPinService` / `PUT /api/plus/security/pin` (needs login password); 5 wrong → locked 30 min
- **Rate limiting / login lockout**: `security/ratelimit/` (in-memory, single instance). Disabled in tests via `application.security.rate-limit-enabled: false`
- **Errors**: throw `ApiException` (status + `error.<key>` message) instead of bare `orElseThrow()`/`IllegalArgumentException` (those become 500)
- Rules: fee tiers and the minimum balance (5) are config, `application.fees` in `application.yml` (`ApplicationProperties.Fees`, `BigDecimal`, quoted), read through `FeeSchedule` (validated at startup; tests use the same defaults from the Java class). The fee is stored in `transaction_record.fee` (not `exchange_rate`, which is 1: there is no FX). Limits in `TransactionLimitServicePlus` (Kinshasa time)
- **Admin CRUD `/api/bank-accounts`** (`BankAccountServicePlus.admin*`, row locked by id first): `balance` is read-only (create → 0.00, PUT keeps it, PATCH drops it); an account in use (balance ≠ 0 or any transaction/ledger entry) keeps `accountNumber`/`currency`/owner/`accountType` and cannot be deleted (409 `accountinuse`). Never pass a nested `user` to the MapStruct `partialUpdate` (it mutates the owner `User`). Never add another path that sets a balance without a ledger entry
- **Pushes**: never call `ExpoPushService` inside a transaction; `NotificationServicePlus` publishes `PushNotificationRequestedEvent`, sent by `PushNotificationListener` AFTER_COMMIT (`ExpoPushService` returns `Mono<PushResult>`, retries transient errors; the outcome sets the notification `PENDING` → `SENT`/`FAILED` and drops `DeviceNotRegistered` tokens). Push `data.type` values the app routes on: `TRANSACTION_ALERT`, `KYC_STATUS` (KYC approve/reject, `KycReviewService`); document any new type in the mobile guide
- All amounts are `BigDecimal`, scale 2, `RoundingMode.HALF_UP`.

## Testing notes
- ITs that exercise the PIN or anything REQUIRES_NEW must NOT be `@Transactional` (see `TransactionFlowIT`): create committed data and delete it in `@AfterEach` **inside a `TransactionTemplate`** (the test pool is `auto-commit: false`, plain `JdbcTemplate` deletes get rolled back)
- If test resources look stale (e.g. a config change is ignored), run with `clean`: the IDE also writes into `target/`
- The shared test pool has 1 connection, so "parallel" requests in normal ITs never overlap. Real lock contention lives in `ConcurrentTransfersIT` (`@TestPropertySource` pool of 8, own context): add a case there for any new money flow
- Known pre-existing failures (not regressions): 81 `createdAt` JSON-format failures in `BankAccountResourceIT`/`IdempotencyRecordResourceIT`/`LedgerEntryResourceIT`, 38 in `NotificationResourceIT`, and 2 in `AccountResourceIT` (registration auto-activates users, so JHipster's "re-register non-activated user" tests can't pass)

## Security config
`config/SecurityConfiguration.java`: `/api/admin/**` → ROLE_ADMIN. The 8 JHipster-generated CRUD paths (`/api/bank-accounts/**`, `/api/transaction-records/**`, `/api/ledger-entries/**`, `/api/transaction-fees/**`, `/api/transaction-limits/**`, `/api/idempotency-records/**`, `/api/notifications/**`, `/api/user-details-accounts/**`) → ROLE_ADMIN, both by URL rule and by class-level `@PreAuthorize`; `AdminOnlyCrudResourcesIT` guards this. The nested customer paths `/api/bank-accounts/plus/**` and `/api/ledger-entries/plus/**` are matched first and stay authenticated-only. Everything else under `/api/**` → just authenticated. Put new customer endpoints under `/api/plus/...` and check ownership in the service; when adding a matcher, keep the specific `/plus` rules before the admin-only CRUD rules. `GET /api/users` and `/management/prometheus` are admin-only. `RateLimitFilter` runs right after JWT authentication.

## Authentication & sessions (TODO.md item 13)
- Login `POST /api/authenticate` → `SessionService.login` creates a `UserSession` (`DEVICE` with keys / `ADMIN` / `LEGACY`) and returns `AuthTokensDTO`. Access tokens come from `AccessTokenService` (claims `sid`, `did`, `jti`); never mint JWTs elsewhere
- `web/filter/DeviceBindingFilter` (after JWT auth + rate limit): every JWT must have an active `sid`; DEVICE sessions must sign each request (`security/device/DeviceSignatureVerifier`, `CanonicalRequest`); `TRANSACTION_SIGNED` lists the endpoints needing the biometric `X-Tx-Signature` — add new money endpoints there
- Refresh `POST /api/auth/refresh` (public; body buffered by the filter, verified in `SessionService.refresh`): rotation + reuse detection
- Revoke sessions by publishing `RevokeUserSessionsEvent` (keeps services decoupled from `SessionService`)
- Rollout flag `application.security.sessions.device-binding` (`DEVICE_BINDING_MODE` env, `optional`|`enforce`)
- Tests: `MockMvc` with `user(...)`/`@WithMockUser` skips the device filter (not a JWT). To test the real chain, use real JWTs + `TestDeviceKey` like `DeviceSessionIT`

## Working rules
- Never commit secrets; config secrets should come from environment variables.
- Any change to money movement needs: row locking, idempotency, a balanced ledger, and tests (including concurrency).
- Schema changes go through new Liquibase changesets — never edit an already-applied changelog.
- Never commit changes unless i ask you to do so.
- Everytime you add new entity, you should add it also in jdl file
- Create file called mobile guide integration if doesn't exist and you going to add all information about the mobile integration needed after any changes you going to add, this file must to be well documented
